# OpenFunASR 输出质量测试计划：先暴露问题，再判断原因

诊断基线日期：2026-10-29。本文保留修复前发现与后续音频测试计划。同日已完成一轮源码修复，当前结果见[修复记录](OUTPUT_QUALITY_FIXES.zh-CN.md)；下文“已复现”表格是修复前证据。

目标：弄清数字、停顿标点、中英文混说分别在什么条件下出错，错误出现在哪一层，以及对日常输入的影响。先得到可复现的问题清单，不先选替代模型，也不先堆修正规则。

## 1. 已经完成的检查与边界

- 已读取本目录源码、现有回归测试和集成测试；运行现有 `test_openfunasr.py`，通过。
- 已直接调用现有后处理函数，构造文本输入暴露边界问题。可复跑脚本：[`probe_output_quality.py`](../scripts/probe_output_quality.py)。这不是模拟一个新实现。
- 本次没有录制语音、运行真实语音识别、操作输入框或替换应用。因此不能给出用户实际口音、麦克风或中英文混说的准确率。
- 修复前源码 SHA-256：`719b31bf304e0fe2f11c5ee5b8eb5399e130fe0d1cc19ea0310bd4e2af7eac51`。
- 本目录和另一份历史开发目录中的数字、标点、命令构造及转录入口函数经 AST 比较一致；这不能证明已安装二进制与本目录完全一致。真实音频测试前需核对实际运行库、模型与应用版本。

已有集成测试只要求“语音有非空输出、静音无输出”，不比较内容。现有回归测试甚至把“多个语音片段时将句号改成逗号”作为期望行为。因此，原测试通过与输出质量有问题可以同时成立。

## 2. 已复现的问题及分析

下列“输入”是送给后处理的人工文本，不是本次真实识别结果。所有期望均针对表中指定语义。

| 问题 | 输入与条件 | 实际输出 | 判断和原因 |
|---|---|---|---|
| 小数百分比损坏 | 增长百分之三点五。 | 增长3%点五。 | 确认后处理错误：百分比规则先只匹配整数部分，破坏了后续小数匹配的上下文。零点五也有同类问题。 |
| 约数变成确定的大数 | 要等三四分钟。 | 要等34分钟。 | 确认后处理错误：数字串按逐位数字拼接，量词触发转换，未区分约数。 |
| 人数约数失真 | 需要两三个人。 | 需要23个人。 | 与上一项同源，直接改变数量含义。 |
| 嵌套大单位算错 | 总额一万亿元。 | 总额100010000元。 | 确认整数解析错误：万、亿按独立累加处理，未表达嵌套单位。此例是低频边界，影响优先级应结合真实使用频率。 |
| 完整句界被合并 | 今天先到这里。明天继续。；片段数为2 | 今天先到这里，明天继续。 | 确认后处理行为：片段数大于1即改写所有符合条件的内部中文句号，没有判断哪个位置是停顿、哪个位置是真正句界。片段数为1时保持原文。真实录音是否触发该条件待测。 |
| 独立问答被误拼 | 有哪些开源的？Python。；明确是问答两句 | 有哪些开源的Python？ | 在该语义下确认误改：短尾词规则会把答案当作前一句尚未说完的名词。需要用音频/上下文区分。 |
| 技术括号内容丢失 | 请调用 foo(bar)，再读取 items[0]。 | 请调用 foo，再读取 items。 | 确认条件性破坏：入口直接删除所有半角圆括号、方括号及内部内容，没有区分注记与正文。尚未验证引擎在口述中是否会正确产出这些符号。 |
| 编号输出格式不一致 | 验证码零零一二三四。 / 验证码是零零一二三四。 | 验证码001234。 / 验证码是零零一二三四。 | 格式差异，非数值识别错误。规则要求标签与数字紧邻；多一个“是”就不转换。 |
| 错误逗号仍残留 | 测试结，果已经出来了。 | 原样保留 | 后处理覆盖有限，不代表逗号由后处理产生。真实音频需检查引擎原文。 |

另有一个暂不判错的观察：“预算一千二元”变成“预算1002元”。口语可能指1200，也可能有其他表达意图；先保留音频并标记歧义，不能用测试脚本擅自补成某个数。

已通过的对照包括整数百分比、完整日期、明确时间、1200这样的明确整数、紧邻标签的前导零编号、部分词语保护、Python 3.12及timeout 3.5秒等文本转换。它们只证明给定文本的后处理结果，不证明英语词或数字能被正确听出来。

### 修复前对三类问题的判断

1. **数字**：已经证实后处理会制造错误，不应先把全部责任归给模型。后续仍需测引擎漏零、听错位数、单位混淆等独立问题。
2. **停顿标点**：当前存在两类不同问题——引擎可能按停顿插入错误标点；后处理又可能把合法句界合并。两者要分别计数，不能用“标点总数减少”作为改进指标。
3. **中英文混说**：目前无法判断声学识别质量。源码调用没有显式传入语言、热词或自定义提示参数；这仅是调用方式，不证明运行库不支持，也不证明它是根因。需要用相同术语的纯英文和混说样本比较。

## 3. 必须保留的证据链

当前链路如下：

`录音 → 时长/能量检查 → whisper.cpp/Silero检测并计数 → 完整音频送入Fun-ASR（命令另带FSMN VAD模型） → stdout原文 → 数字/标点等后处理 → 输出文本`

外层检测结果用于静音拦截和后处理片段数参数；代码没有用外层检测出的片段逐段调用识别。两层VAD的作用不要混为一谈。

每条真实音频至少保留：

| 字段 | 内容与用途 |
|---|---|
| 样本标识 | `case_id`、读法变体、录音编号、重复推理编号 |
| 原始音频 | WAV路径及SHA-256、时长、采样率、声道、位深；录音不可被评分过程覆盖 |
| 标注 | 实际说出的文字、关键数字/英文/单位、可接受形式、不得断开的词组、必须保留的句界；停顿时刻及实测时长 |
| 环境 | 麦克风、距离、噪声情况、应用/源码/二进制版本或哈希、模型哈希、实际命令和参数 |
| 检测结果 | 能量检查结果、外层VAD片段数、可取得的起止时间与日志；取不到的字段写未知 |
| 引擎原文 | stdout原样、stderr、退出码、推理耗时；不要只保存清洗后的字符串 |
| 最终文本 | 后处理输出及文本diff；必要时离线记录每一步的中间文本 |
| 评分 | 数字语义、英文词、句界、漏字/增字、后处理新增/修复错误、严重度、证据等级 |

当前应用正常处理后会删除临时录音，日志主要保留原文长度、数字转换数、句号改写数及VAD片段数，不能据此还原历史识别错误。离线测试应使用自有音频副本直接调用相同二进制，再调用现有后处理，保留两份文本；如复用 `runTranscription()`，必须使用一次性副本，不传唯一原件。实测UI阶段再核对离线最终文本与真实粘贴是否一致。

录音和结果保存在仓库外或已忽略的本地结果目录，不提交到Git；使用虚构号码和金额。不要为此改动常驻应用的日志设置或录音行为。

## 4. 测试语料：32条基础句

朗读时保持日常口音。数字按表内汉字读；英文照日常说法读，API和PR按字母读。方括号里的停顿说明不读出。参考文本先按语义评分，不要求每个合理标点只有一种写法。

### A. 数字，12条

| ID | 朗读内容 | 关键检查点 |
|---|---|---|
| N01 | 今天是二零二六年十月二十九日，下午三点十五分开会。 | 2026、10、29和3:15分别正确；日期和小数不能混用。 |
| N02 | 温度负三点五度，误差零点零五。 | -3.5、0.05，不能丢负号、零或小数位。 |
| N03 | 增长百分之三点五，下降百分之零点五。 | 3.5%、0.5%，同时检查原文和后处理。 |

### B. 停顿与句界，8条

竖线是加停顿的位置，不读出。每句保留自然读法，再录约0.3、0.8、1.5秒三个停顿变体；记录实际停顿，不把目标时长当测量结果。另可从同一录音中的静音区延长停顿做控制实验，但不得裁断音素，也不能把拼接样本当自然语音。

| ID | 朗读内容 | 关键检查点 |
|---|---|---|
| P01 | 这是我对｜结果的要求。 | 停顿不应拆开“对结果的要求”。 |
| P02 | 请先检查测试｜结果，再决定下一步。 | “测试结果”内部不应乱断句。 |
| P03 | 今天先到这里。｜明天继续。 | 两个独立句子，不能因多个检测片段一律合并。 |
| P04 | 如果今天来不及，｜我们就明天处理。 | 正常从句逗号可保留，不能全删标点。 |
| P05 | 有哪些开源的？｜Python。 | 设定为问题和回答；不能拼成“有哪些开源的Python”。 |
| P06 | 对，｜我同意。 | “对”是回应，不是介词。 |
| P07 | 有哪些值得去的｜旅游景点？ | 句中停顿不应提前出现问号。 |
| P08 | Please review the PR.｜Then run pytest. | 英文独立句；与中文句界策略做对照。 |

### C. 中英文混说，8条

| ID | 朗读内容 | 关键检查点 |
|---|---|---|
| E01 | 用 Python 处理这个 JSON，再调用 API。 | Python、JSON、API，不应音译成无关汉字或漏掉。 |
| E02 | Use Python to process this JSON and call the API. | 与E01共享术语的纯英文对照；不据此单独断定模型根因。 |
| E03 | 先 review 这个 PR，然后 merge 到 main。 | review、PR、merge、main在连续语言切换中是否稳定。 |
| E04 | 执行 git status，再运行 pytest。 | 两个命令名准确，不能凭大意相近判通过。 |
| E05 | Python 三点一二和 Node 二十二都装好了。 | Python 3.12、Node 22，版本号不能被当时间。 |
| E06 | 把 timeout 设成三点五秒，retry 改成三次。 | 英文词、数字、单位正确对应，不串到另一参数。 |
| E07 | 打开 config 点 json 文件，检查 README。 | 文件名config.json的内容准确；大小写表现单独记。 |

## 5. 分阶段执行，避免一次铺太大

### 第一轮：低成本找可复现错误

1. **文本后处理探针已执行**：24个案例保留输入、期望、实际输出、片段数与源码哈希。它只隔离后处理问题。
2. **首批真人录音尚待执行**：N01、N02、N03、N05、N07、N11、P01、P03、E01、E02、E06、X01，共12条自然读法；P01、P03、X01各加一个约0.8秒停顿版，共15条。
3. 用同一套当前运行库和模型逐条跑识别。固定音频先跑一次，保留全部结果；只将失败或结果可疑的音频再推理2次，共3次，不反复重录直到“成功”。
4. 把问题分成：原文已错、后处理新增、后处理未修、音频歧义、检测漏过/截断待证。结果波动与固定错误分开。
5. 首批已能明确回答的错误不继续堆样本；尚不能判断的类型再扩展到完整60条。

### 第二轮：只对失败点做对照

| 对照 | 只改变什么 | 可以说明什么 / 不能说明什么 |
|---|---|---|
| 相同音频重复推理 | 推理次数 | 区分同一音频的稳定性；不能当成多个独立样本计算准确率。 |
| 原文与最终文本 | 是否应用现有后处理 | 直接观察后处理收益和损害。 |
| 相同原文，片段数设1与真实值 | 离线后处理参数 | 隔离全局改句号逻辑；不能证明VAD把语音分错了。 |
| 同一句自然读法与停顿变体 | 停顿长度 | 观察停顿敏感性；真人重录还存在发音差异，要据实记录。 |
| 同一术语，纯英文与混说 | 语言上下文 | 发现切换相关问题；不是对单一声学因素的严格证明。 |
| 一种条件重复自然录音3次 | 实际发音 | 区分单次读法偶然性；仅对首轮关键失败补录。 |

只有原文错误与分段位置存在证据关联时，再检查内部VAD切段或识别上下文。更换模型、量化、热词、解码参数属于后续解决方案实验，此阶段先不混进基线。

### 第三轮：形成问题清单与后续修复优先级

每个问题只需一条主记录：现象、最小样本ID、音频、原文、最终文本、期望/可接受变体、重复结果、归因证据、影响与优先级。相同根因的多个句子归到同一问题，但保留各自证据。

优先处理会静默改变数值、单位、否定或技术标识的错误；其次是影响句意的断句；最后是空格、大小写、数字表现形式。优先级同时考虑真实使用频率，不能仅靠极端例子排序。

在后续开始修复前，另录8条未见过的新措辞作为保留集：数字3条、句界2条、混说2条、交叉1条；定稿后不拿来设计特例规则。它们不包含在本轮60条中。

## 6. 怎么评分

不要用一个“总体准确率”盖住数字与句界问题，也不要把标准答案写成唯一标点字符串。

| 维度 | 记录方式 |
|---|---|
| 关键数字语义 | 正确数字实体数 / 无歧义数字实体总数。逐项核对正负、数值、单位、范围或约数属性；编号按字符串核对前导零。 |
| 英文词/技术标识 | 正确关键项数 / 关键项总数。普通词的大小写只算格式；命令、路径等有功能影响时严格核对。不把英文被译成中文算原文保真。 |
| 句界和标点 | 按词间位置标注“禁止断开、必须独立成句、可有可无”。记录禁断处误插数、必须句界丢失数、逗号与句号类型误用；合理风格差异单列。 |
| 内容错字 | 中文CER、英文WER可作辅助；冻结去标点/大小写等规则，同时保留原样评分。不通过数字归一化掩盖34和三四的语义差别。 |
| 后处理收益/损害 | 原文错误被修复的实体或句界数；原文正确而被改错的实体或句界数；原来就错而保留的数量另记。 |
| 稳定性 | 同一音频3次输出有几种结果，关键数字/英文/句界是否变化。 |
| 使用成本 | 每条需改几处关键内容、是否整句重说；延迟仅辅助记录，首轮不做速度优化。 |

数字中文或阿拉伯写法、合理中英空格、普通专名大小写，默认先计格式偏好。不能为了满足格式要求把正确含义改错。歧义句先复听并标注，不能混进严格准确率分母。

本轮是发现问题，不设虚假的“95%就通过”。每类报告明确分母和具体失败，尤其不能拿24条刻意挑选的文本探针计算产品准确率。

## 7. 本阶段的完成标准

- 对数字、停顿、中英文混说分别给出“已复现 / 本批未复现 / 尚未测试”，不将未测写成通过。
- 每个已确认问题有最小输入与输出证据；音频层问题必须有对应录音，文本探针不能替代。
- 至少能分清错误是在引擎原文还是后处理；无法定位时列出还缺哪一个对照。
- 保留正确对照，知道现有逻辑在哪些输入有效，避免之后修复伤到它们。
- 交付基线报告与按影响排序的问题清单，再决定修什么。本次完成的是计划、源码分析与文本后处理诊断；真人音频基线仍未执行。
